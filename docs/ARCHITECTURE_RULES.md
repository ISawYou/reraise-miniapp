# Правила архитектуры Re-raise

Свод принципов, устоявшихся за время миграции на Repository Layer. Обязателен к соблюдению для любого нового кода, работающего с данными. См. также [REPOSITORY_LAYER_ARCHITECTURE.md](./REPOSITORY_LAYER_ARCHITECTURE.md) (обоснование и домены) и [MIGRATION_PROGRESS.md](./MIGRATION_PROGRESS.md) (статус по фазам).

## Целевая схема

```
Route / Server Component
        ↓
     Feature          (бизнес-логика, валидация, оркестрация)
        ↓
   Repository         (тонкий доступ к данным своего домена)
        ↓
Database Client Layer  (конструирование Supabase-клиента)
        ↓
    Supabase
```

## Принципы

1. **Repository не содержит бизнес-логику.** Валидация, вычисление рейтинга, начисление достижений, расчёт статистики, orchestration завершения турнира, экспорт в Google Sheets — ничего из этого не переносится в Repository. Всё это остаётся в `features/*.ts` / `lib/*.ts` / route handler'ах.

2. **Repository работает только со своим доменом.** Один Repository = одна таблица или один тесно связанный агрегат (пример осознанного агрегата: `TournamentLiveStateRepository` объединяет `tournament_live_entries` + `tournament_player_eliminations`, потому что обе таблицы описывают состояние одного и того же — идущего сейчас турнира). Если метод Feature затрагивает несколько таблиц — он вызывает несколько Repository, а не смешивает запросы внутри одного.

3. **Feature оркестрирует несколько Repository.** Каскадные операции (например, удаление игрока: `tournament_live_entries` → `player_achievements` → `results` → `registrations` → `players`), многошаговые бизнес-процессы (регистрация с проверкой вместимости турнира, завершение турнира с начислением рейтинга) — это Feature-уровень, вызывающий Repository по очереди. Repository никогда не вызывает другой Repository.

4. **Integration Services не являются Repository.** Google Sheets, Telegram (bot API, webhook, WebApp initData, Login Widget), Resend/email — это внешние интеграции с собственными API, а не доступ к нашей БД. У них нет и не будет "провайдера на замену" в смысле `DATABASE_PROVIDER`.

5. **Realtime-подписки — не Repository.** `supabase.channel(...).on("postgres_changes", ...)` — Supabase-специфичный, долгоживущий WS-механизм без прямого аналога в Postgres/Drizzle. Остаётся прямым использованием anon-key клиента (`lib/supabase.ts`) в client component'ах (`app/page.tsx`, `app/tournaments/page.tsx`). Не оборачивается в Repository Layer.

6. **Middleware Edge Runtime может быть исключением.** `middleware.ts` выполняется в Edge Runtime и намеренно не использует `import "server-only"`-зависимости (каждый Repository несёт такой guard) и Node-only API (использует Web Crypto вместо Node `crypto`). Пока middleware не переведён на Node Runtime — прямой запрос к Supabase внутри него остаётся законным исключением, а не нарушением архитектуры.

7. **Repository использует Database Client Layer.** Ни один Repository не конструирует Supabase-клиент самостоятельно (`createClient(...)` напрямую) — только через `getSupabaseServer()` из `@/lib/database`. Это единственное место, которое знает, какие env-переменные и опции нужны клиенту.

8. **Любой новый код должен обращаться к данным только через Repository.** Если для нужной операции ещё нет метода в существующем Repository — добавляется метод (или новый Repository, если это новый домен), а не прямой вызов `supabase.from(...)` в фиче или роуте.

9. **`DATABASE_PROVIDER` появится только после завершения Supabase Repository Layer.** Ветвление на провайдера бессмысленно, пока существует только одна реализация — это мёртвый код и преждевременная абстракция. Сначала — второй провайдер (`PostgresXxxRepository`), потом — ветвление в `lib/repositories/<domain>/index.ts`.

10. **Публичный контракт приложения не меняется в рамках миграционных фаз.** HTTP-статусы, форма ответов, экспортируемые имена и сигнатуры функций — идентичны до и после переноса на Repository. Любое расхождение (например, разница в сериализации `null` vs отсутствующего поля) фиксируется явно в отчёте по фазе, а не скрывается.

## Практические следствия

- **Insert/Patch-типы репозиториев — permissive (`Partial<Row>`), а не новый строгий контракт.** Обёртка над существующим вызовом не должна запрещать то, что раньше было разрешено.
- **JOIN-запросы остаются внутри Repository ровно в том виде, в котором они были в Supabase-запросе.** Разбивать embedded-select на два отдельных запроса с ручным join в коде — это поведенческое изменение (лишний round-trip), а не рефакторинг.
- **Разные вызывающие с разным текстом ошибки для одной и той же операции** (например, 11 разных сообщений для одного `update()`) — Repository бросает нейтральную ошибку с сырым текстом от Supabase, а конкретное сообщение остаётся на стороне вызывающего кода (Feature/route), который оборачивает вызов в свой `try/catch`.
- **Дублирование тривиальных мапперов между репозиториями/фичами (`mapTournamentRow` и т.п.) — приемлемо**, если два домена законно нуждаются в одной и той же трансформации Row→Domain для разных целей (например, `ResultRepository` встраивает полную строку `tournaments` в JOIN, но не берёт на себя маппинг чужого домена).
